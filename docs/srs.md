# Специфікація вимог до програмного забезпечення (SRS)

Інженерний контракт вимог до системи **«Шипшина»** за стандартом **ISO/IEC/IEEE 29148**.

## 1. System Context (контекст системи)

**Призначення (Scope).** Система забезпечує планування ризик-зважених маршрутів доставки вантажів
БПЛА та моніторинг рейсів у середовищі з динамічними загрозами (РЕБ/ППО). Межі системи охоплюють
формування доставки, побудову та перерахунок маршрутів, прийом і обробку телеметрії, детекцію та
класифікацію втрати, ведення реєстру загроз і керування доступом. Поза межами — керування польотом
на борту, фізичне обслуговування та бухгалтерія.

**Зовнішні актори та інтерфейси:**

- **Оператор / Аналітик / Адміністратор** — веб-інтерфейс (HTTPS/REST, WSS).
- **Борт БПЛА** — джерело телеметрії (MQTT/TCP, TLS).
- **Метео-API** — зовнішні погодні дані (HTTPS/REST).
- **OSINT-джерела** — відкриті дані про засоби РЕБ/ППО (HTTPS/REST).
- **Картографічний провайдер** — тайли мапи (HTTPS).

## 2. Functional Requirements (функціональні вимоги)

- <a id="srs-fun-01"></a>**SRS-FUN-01.** Система **повинна** дозволяти оператору створювати доставку
  із заданням точок призначення та параметрів посилки й автоматично підбирати сумісний клас
  контейнера й тип дрона.
- <a id="srs-fun-02"></a>**SRS-FUN-02.** Система **повинна** будувати щонайменше 2–3 альтернативні
  маршрути з чисельною Pдолету, ETA, витратою заряду та розкладкою внеску кожного фактора.
- <a id="srs-fun-03"></a>**SRS-FUN-03.** Система **повинна** перераховувати маршрути подієво при
  зміні даних про загрози або погоду та пропонувати оновлений варіант на підтвердження оператора.
- <a id="srs-fun-04"></a>**SRS-FUN-04.** Система **повинна** приймати й буферизувати телеметрію та
  відображати позиції активних дронів на мапі в реальному часі.
- <a id="srs-fun-05"></a>**SRS-FUN-05.** Система **повинна** детектувати мовчання борту (T1),
  оцінювати ймовірну позицію та класифікувати втрату (T2: SILENT / PRESUMED_LOST / SHOT_DOWN) із
  формуванням інциденту.
- <a id="srs-fun-06"></a>**SRS-FUN-06.** Система **повинна** вести реєстр загроз РЕБ/ППО з ручним
  введенням та OSINT-гіпотезами, розрізняючи походження й достовірність.
- <a id="srs-fun-07"></a>**SRS-FUN-07.** Система **має** виконувати просторові запити «загрози в
  коридорі маршруту» через просторовий індекс (PostGIS GiST, ST_DWithin).
- <a id="srs-fun-08"></a>**SRS-FUN-08.** Система **повинна** розмежовувати доступ за ролями (RBAC) і
  журналювати дії із загрозами й рейсами в незмінний audit log.

## 3. Non-Functional Requirements (NFRs Matrix)

| ID | Категорія | Вимога та числова метрика |
|---|---|---|
| <a id="srs-nfr-perf-01"></a>**SRS-NFR-PERF-01** | Продуктивність | p95 latency критичних REST API **повинна** не перевищувати 200 мс при 500 RPS |
| <a id="srs-nfr-perf-02"></a>**SRS-NFR-PERF-02** | Реалтайм | Затримка телеметрії на мапі **має** не перевищувати 1.5 с; оновлення ≥ 1 Гц |
| <a id="srs-nfr-perf-03"></a>**SRS-NFR-PERF-03** | Масштабованість | Прийом телеметрії ≥ 5000 пов./с; підтримка ≥ 300 одночасних рейсів |
| <a id="srs-nfr-perf-04"></a>**SRS-NFR-PERF-04** | Планувальник | Побудова маршрутів ≤ 3 с (p95); перерахунок на подію ≤ 5 с |
| <a id="srs-nfr-sec-01"></a>**SRS-NFR-SEC-01** | Безпека | Автентифікація **повинна** базуватися на OAuth 2.0/OIDC з підписаними JWT (RS256), TTL ≤ 15 хв |
| <a id="srs-nfr-sec-02"></a>**SRS-NFR-SEC-02** | Безпека | Усі канали **повинні** використовувати TLS 1.3; PII шифрується at-rest (AES-256) |
| <a id="srs-nfr-sec-03"></a>**SRS-NFR-SEC-03** | Комплаєнс | Система **повинна** відповідати OWASP API Security Top-10 (2023) |
| <a id="srs-nfr-rel-01"></a>**SRS-NFR-REL-01** | Доступність | Доступність трекінгу ≥ 99.9%; деградація планувальника не спиняє трекінг |
| <a id="srs-nfr-rel-02"></a>**SRS-NFR-REL-02** | Відмовостійкість | Міжсервісні виклики **повинні** мати timeout ≤ 2 с, retry з backoff, circuit breaker та DLQ |
| <a id="srs-nfr-rel-03"></a>**SRS-NFR-REL-03** | Ідемпотентність | Обробка телеметрії **повинна** бути ідемпотентною за (flightId, seq) із дедуплікацією |

## 4. Verification Criteria (критерії верифікації)

| Вимога | Метод та інструмент верифікації |
|---|---|
| SRS-NFR-PERF-01 | Автоматизований стрес-тест **k6** за сценарієм Load/Spike Testing; поріг p95 < 200 мс @ 500 RPS у CI (quality gate) |
| SRS-NFR-PERF-03 | k6 constant-arrival-rate + моніторинг Kafka consumer lag у **Prometheus/Grafana** |
| SRS-NFR-PERF-04 | Модульні тести алгоритму (**JUnit**) на еталонних сценаріях; вимірювання тривалості побудови |
| SRS-NFR-SEC-01 | Інтеграційні тести автентифікації (**Postman/Newman**), перевірка підпису JWT; **OWASP ZAP** |
| SRS-NFR-SEC-03 | Статичний аналіз **SonarQube** + сканер залежностей та образів **Trivy** у CI (0 critical/high) |
| SRS-NFR-REL-02 | Контрактні тести + fault injection (**Testcontainers + Toxiproxy**): circuit breaker та DLQ |
| SRS-NFR-REL-03 | Інтеграційні тести дедуплікації (повторна доставка повідомлення з тим самим seq) |
| SRS-FUN-04 | Інтеграційний тест WebSocket (вимір latency) та навантаження симулятором дрона |

## 5. Glossary (глосарій)

| Термін | Дефініція |
|---|---|
| **BVLOS** | Beyond Visual Line of Sight — польоти поза межами прямої видимості оператора |
| **Pдолету** | Ймовірність успішного дольоту маршрутом як добуток ймовірностей виживання по зонах загроз |
| **РЕБ** | Радіоелектронна боротьба — глушіння каналу керування та супутникової навігації (GNSS) |
| **Dead reckoning** | Числове числення поточної позиції від останнього відомого вектора стану борту |
| **Event-driven** | Архітектурний стиль, де компоненти взаємодіють асинхронно через події у брокері |
| **Idempotency** | Властивість операції давати той самий результат при повторному виконанні |
| **GiST-індекс** | Generalized Search Tree — просторовий індекс PostGIS для запитів близькості |
| **JWT** | JSON Web Token — підписаний токен для автентифікації та передачі прав (RS256) |
