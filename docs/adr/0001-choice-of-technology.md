# ADR-001: Вибір PostgreSQL + PostGIS як геопросторового ядра системи

- **Статус:** Approved (Затверджено)
- **Дата:** 2026-10-31
- **Автор:** Добрянський В. В.

## Context (контекст)

Ядро системи потребує сховища, що одночасно забезпечує (1) ефективні просторові запити «загрози в
коридорі маршруту» ([SRS-FUN-07](../srs.md#srs-fun-07), усунення вузького місця B5) та (2)
транзакційну цілісність для доставок і життєвого циклу рейсів. Обмеження зі специфікації: просторовий
запит має виконуватися через індекс (без перебору O(n)), а побудова маршрутів — вкладатися в
[SRS-NFR-PERF-04](../srs.md#srs-nfr-perf-04) (≤ 3 с).

## Decision Drivers (рушійні фактори)

- Зрілість і продуктивність просторових операцій (радіус, перетин, буфер).
- Транзакційність (ACID) та узгодженість даних.
- Latency просторового запиту (ціль — одиниці мілісекунд).
- FinOps: вартість керованого сервісу та експлуатаційна складність.
- Наявні компетенції команди (SQL) та technical debt.

## Considered Options (розглянуті альтернативи)

1. **PostgreSQL + PostGIS** — реляційна СУБД зі зрілим геопросторовим розширенням (GiST-індекси,
   ST_DWithin, ST_Intersects).
2. **MongoDB** — документна СУБД з геопросторовими індексами 2dsphere та гнучкою JSON-схемою.
3. **Elasticsearch (geo)** — пошуковий рушій із geo_shape/geo_distance для просторових запитів.

| Критерій (2026) | PostgreSQL + PostGIS | MongoDB | Elasticsearch |
|---|---|---|---|
| Просторові операції | Повні (ST_DWithin, ST_Intersects, буфери) | Базові (2dsphere, $near) | Для пошуку; слабші для топології |
| ACID / узгодженість | Сильна (ACID) | Обмежена (транзакції дорожчі) | Eventual consistency |
| Latency запиту | Одиниці мс по GiST | Одиниці–десятки мс | +вартість індексації |
| FinOps | Низька–середня (managed Postgres) | Середня (Atlas) | Висока (RAM-інтенсивний) |
| Technical debt | Низький (SQL-компетенції) | Середній (нова модель) | Високий (окремий стек) |

## Decision (рішення)

Обрано **PostgreSQL + PostGIS** як основне геопросторове й транзакційне сховище. Ключовим фактором є
поєднання зрілих просторових операцій (GiST + ST_DWithin для [SRS-FUN-07](../srs.md#srs-fun-07)) із
транзакційною цілісністю життєвого циклу доставок у межах одного сховища, що усуває потребу в
синхронізації між окремими базами. Часові ряди телеметрії винесено в TimescaleDB (окреме рішення),
оскільки вони мають інший профіль навантаження.

## Consequences (наслідки, Trade-offs)

**Позитивні:**

- Просторовий запит [SRS-FUN-07](../srs.md#srs-fun-07) виконується за GiST-індексом за одиниці
  мілісекунд — вкладається в [SRS-NFR-PERF-04](../srs.md#srs-nfr-perf-04).
- ACID-транзакції для станів доставки та рейсів без додаткової координації.
- Низький technical debt: команда володіє SQL; широка екосистема та managed-пропозиції.

**Негативні (приховані ризики):**

- Записи масштабуються переважно вертикально; для аналітики та важких читань потрібна read-репліка
  (додаткова FinOps-вартість).
- Експлуатаційна складність PostGIS (версії розширень, міграції геометрії).
- Жорстка схема менш гнучка до частих змін структури — пом'якшується міграціями (Liquibase) та JSONB
  для напівструктурованих полів.
